# 12. 家族共有の設計（たたき台）

> ステータス: Draft v0.1 / 2026-11-10
> 前提: [11](./11_phase2_plan.md) の F1。ユースケースは [02](./02_use_case_scenarios.md) C-5、画面は [03](./03_screens.md) P-08・C-06、データは [04](./04_data_model.md) 5.1
> 現地からの報告（F2）は家族共有の上に作るため、この設計では権限（4.2）と画面の入口（7章）だけ決める

---

## 1. やりたいこと

- 家族で**同じ地点（実家・子どもの学校など）を一緒に見る**。誰か1人が登録すれば、家族全員のホームとタイムラインに出る
- 警報・地震が出たら、**通知をオンにしている家族全員に届く**
- 招待はリンクを送るだけ（LINE などで共有できる）。相手はアカウントを作ってリンクを開けば参加できる

### 1.1 作らないもの（Phase 2）

- 複数の家族グループへの所属（1人1グループ。2.1）
- 家族の中の細かい権限（「閲覧だけ」など）。家族は **owner** と **member** の2つだけ
- メンバーの位置情報の共有（このサービスは地点を見守るもので、人の居場所は扱わない）

---

## 2. 決めたこと

| # | 決めること | 決定 | 理由 |
| --- | --- | --- | --- |
| D1 | 1人が入れる家族グループの数 | **1つだけ** | 認可で引く所有者が最大2つ（自分・家族）で済む。地点の一覧・上限・通知の作りが単純になる。親世帯と子世帯の両方に入りたい場合は Phase 3 の組織で考える |
| D2 | 個人の地点を家族の地点に移せるか | **移せる（個人 → 家族の一方向）** | すでに登録した「実家」を、登録し直さずに共有できる。暗号化の AAD は地点の ID だけなので、暗号化し直さずに移せる。家族 → 個人は、家族のデータを1人が持ち出すことになるため作らない |
| D3 | 家族の地点の通知を誰に送るか | **メールの通知をオンにしているメンバー全員** | 利用者ごとの通知の設定（今の `emailEnabled`）をそのまま使う。家族の地点だけ止めたい人は Phase 2 の後半で地点ごとの設定を足す |
| D4 | 招待リンクの使い方 | **1つのリンクで1人だけ（使い切り）、72時間で失効** | リンクが転送されて家族でない人が入るのを防ぐ。家族が3人なら3つ作る |
| D5 | 上限 | メンバー 10人、家族の地点 5件（無料）、有効な招待 5件 | 家族の地点は個人の地点（3件）とは別に数える |
| D6 | owner の退会 | 一番前から参加しているメンバーに owner を引き継ぐ。ほかにメンバーがいなければ、家族と家族の地点を削除する | owner が退会しただけで、残った家族が地点を失わないようにする |

## 3. データ（[04](./04_data_model.md) 5.1 の `app` テーブル）

| エンティティ | PK | SK | 主な属性 |
| --- | --- | --- | --- |
| Organization | `ORG#<orgId>` | `META` | name（20字まで）, type=`family`, plan, memberCount, locationCount, createdBy, createdAt, writtenBy |
| Membership | `ORG#<orgId>` | `MEMBER#<userId>` | role（`owner` / `member`）, invitedBy, joinedAt, writtenBy / GSI1: `USER#<userId>` / `ORG#<orgId>` |
| User（追加の属性） | `USER#<userId>` | `PROFILE` | familyId（所属している家族。なければ属性なし）, displayName（家族に見せる名前。20字まで。任意） |
| Invite | `INVITE#<sha256(token)>` | `META` | orgId, createdBy, expiresAt（TTL 72時間） |
| Location | `OWNER#O#<orgId>` | `LOC#<locId>` | 個人の地点と同じ（5.2）。`createdBy` を足す |

- **所属の正は Membership**。User の `familyId` は「どの家族を引けばよいか」の目印で、認可のたびに Membership を GetItem して確かめる（目印だけを信用しない）
- 参加・脱退・削除は TransactWriteItems で、Membership・User の `familyId`・Organization の `memberCount` を同時に更新する（条件付き書き込みで上限と二重参加を防ぐ）
- メンバーの一覧には `displayName` だけを出す。**メールアドレスは家族にも見せない**（[07](./07_security.md) 3.5 の最小化）。未設定なら「メンバー1」のように表示する
- 招待のトークンは推測できない乱数（128ビット以上）で、DB にはハッシュだけを置く。受け入れたら条件付きで削除し、2回は使えない
- 地点を家族に移すときは、TransactWriteItems で「個人の地点の削除 ＋ 家族の地点の作成 ＋ AreaIndex の `ownerKey` の更新 ＋ 件数の更新」を行う。タイムライン（`LOC#<locId>`）は地点の ID で引くため、そのまま引き継がれる

## 4. 認可（[07](./07_security.md) 3.2）

### 4.1 地点を引く

今は「トークンから引いた userId の `OWNER#U#<userId>` で地点を引く」こと自体が認可になっている（`ownLocation`）。これを、**その利用者が触れる所有者の一覧**で引く形に広げる。

1. トークンの `sub` → `userId`（今と同じ）
2. User の `familyId` があれば、`ORG#<familyId>` / `MEMBER#<userId>` を GetItem し、あれば所有者の一覧に `OWNER#O#<familyId>` を足す
3. 地点は「自分 → 家族」の順に GetItem する（どちらにもなければ 404。存在の有無を漏らさない）

- この処理はミドルウェアの1か所に置き（`accessibleOwners`）、ハンドラは所有者のキーを自分で組み立てない
- **リクエストに orgId を含めない**。家族は常にトークンの利用者から引く（[CLAUDE.md](../CLAUDE.md) の認可の決まり）

### 4.2 操作ごとの権限

| 操作 | 自分の個人の地点 | 家族の地点（owner） | 家族の地点（member） | ほかの人 |
| --- | :-: | :-: | :-: | :-: |
| 閲覧（地点・タイムライン） | ✓ | ✓ | ✓ | 404 |
| 編集・削除 | ✓ | ✓ | ✓（作った人だけ削除できる） | 404 |
| 現地からの報告（F2） | - | ✓ | ✓ | 404 |
| 個人 → 家族に移す | ✓ | - | - | 404 |

| 家族の操作 | owner | member | 家族でない人 |
| --- | :-: | :-: | :-: |
| 家族の情報・メンバーの一覧を見る | ✓ | ✓ | 404 |
| 名前の変更・招待の作成 | ✓ | | 403 |
| メンバーを外す | ✓（自分以外） | | 403 |
| 抜ける | owner を引き継いでから | ✓ | - |
| 家族を削除する（家族の地点も消える） | ✓ | | 403 |

- 認可テスト（[08](./08_test_strategy.md) 5.3）: 上の2つの表を、そのままテーブル駆動のテストにする。家族でない人・外されたメンバー・使用済みや期限切れの招待・別の家族の地点の ID を混ぜたリクエストを含める

### 4.3 招待リンク

- URL は `https://<サイト>/invite#<token>` にし、**トークンを URL のフラグメント（`#` の後ろ）に置く**。フラグメントはサーバーに送られず、CloudFront のログにもリファラーにも残らない。画面がフラグメントを読み、ログインのあとで API に POST する
- 受け入れの API はログインが必要。WAF でレート制限をかける（[11](./11_phase2_plan.md) S1）
- 招待の作成・参加・脱退・メンバーの削除・地点の移動は、監査ログ（`audit` テーブル）に記録する

## 5. API（`api/openapi.yaml` に足す）

| メソッド | パス | 内容 |
| --- | --- | --- |
| GET | `/family` | 自分の家族（名前・自分の役割・メンバーの一覧・件数と上限）。入っていなければ 404 |
| POST | `/family` | 家族を作る（自分が owner）。すでに入っていれば 409 |
| PATCH | `/family` | 名前を変える（owner） |
| DELETE | `/family` | 家族を削除する（owner。確認の文字列が必要。家族の地点も消える） |
| POST | `/family/invites` | 招待を作る（owner）。招待の URL と期限を返す（トークンはこのときだけ返す） |
| POST | `/family/leave` | 抜ける（member） |
| DELETE | `/family/members/{memberId}` | メンバーを外す（owner）。`memberId` は家族の中だけで使う ID で、userId は外に出さない |
| POST | `/invites/accept` | 招待を受け入れる（本文にトークン）。上限・二重参加・期限切れは 409 / 410 |
| GET | `/locations` | 個人の地点と家族の地点を返す。各地点に `owner: personal \| family` を付ける |
| POST | `/locations` | 本文の `owner`（`personal` / `family`）で登録先を選ぶ（家族を選べるのはメンバーだけ） |
| POST | `/locations/{locationId}/move-to-family` | 個人の地点を家族に移す |
| PUT | `/me` | `displayName` を設定する |

- 既存の API の形は変えず、属性を足すだけにする（新旧のバージョンの共存。[CLAUDE.md](../CLAUDE.md)）。古い画面は `owner` を無視して表示できる

## 6. 通知

- notifier は、地点の所有者が `OWNER#O#<orgId>` なら Membership を引き、**メールの通知をオンにしているメンバー全員**に送る（今は組織の地点を送らずに捨てている）
- 送った通知の記録（`SENT#`）を**受け取る人ごと**にする: `SENT#<status>:<itemId>:<userId>`。1人目に送ったあとで2人目で失敗してやり直しても、1人目に二度送らない
  - 個人の地点の記録（`SENT#<status>:<itemId>`）は、受け取る人が1人なのでそのまま読めるようにする（古い版の記録との互換）
- 件名に、誰の家族の地点かが分かるよう家族の名前を入れる

## 8. 退会・削除

- member の退会: Membership を消して家族から抜ける。その人が作った家族の地点は家族に残す
- owner の退会: D6 のとおり引き継ぐ。ほかにメンバーがいなければ、家族・家族の地点・タイムライン・招待を消す
- 家族の削除: 家族の地点のタイムライン（`LOC#<locId>`）・AreaIndex・招待もすべて消す。削除の途中で失敗しても、もう一度実行すれば最後まで消える（冪等）
